# Authorization and classification decision contract

Status: **Phase 0 approval candidate**
Requirements: `AUTH-001`–`AUTH-006`, `CLS-001`–`CLS-008`, `AGENT-003`, `AGENT-006`

An operation is allowed only when authentication/trusted context is valid, OpenFGA allows the explicit relationship, the deterministic policy layer allows classification/context/handling/information flow, the provider or direct path can enforce the result, and no explicit deny applies. Missing, expired, revoked, unsupported, or unverifiable input denies. Responses conceal denied existence.

The policy-decision input declares which additional context families an action requires. Data-flow context carries the destination domain and profile-qualified ceilings, organizations, releasability, channel, proposed label, and any reasoned/authorized lowering request. CI context carries runner pool/domain, approved image digest, network/egress, secret scope, artifact label, and deployment environment. Infrastructure context carries admission/storage/backup/restore/integration target, provider, profile-qualified ceiling, encryption, network, and applicable backup/integration identity. A required context family that is absent or unverifiable denies.

The authoritative contracts are the [OpenFGA model](../../policies/openfga/model.fga), [model tests](../../policies/openfga/model-tests.yaml), implementation-neutral [policy input](../../policies/policy-decision/input-v0.1.schema.json), [policy output](../../policies/policy-decision/output-v0.1.schema.json), and [decision table](../../policies/policy-decision/decision-table.yaml). A later ADR selects the evaluator and topology; OPA/Rego is permitted but is not a dependency of these contracts.

Team `parent` is organizational context only; the model intentionally defines no viewer/member/editor relation through a parent. Project owning/contributing Teams also grant nothing without explicit authorization tuples. Restrictive classification policy may cascade only through a named, tested policy rule.

For an Agent, allow is the intersection of delegator authority, agent-specific authority, task scope, runtime/workload identity and security domain, session/environment restrictions, and resource label/handling. Agent assignment is not permission. Revocation is independent of the requester. Directory Groups may be authorization subjects but cannot act.

Every decision carries a consistency fence over the resource version, effective-label revision, OpenFGA tuple revision, and delegation/revocation revision. A protected read or mutation MUST evaluate at or after the latest committed raise, compartment addition, explicit deny, permission removal, or delegation revocation. If that ordering cannot be proven, the operation denies and refreshes policy state; a previously cached allow is never served across the fence. Label raises and revocations commit before invalidation events are released, and consumers stop serving affected projections until they reach the new fence. Rollback never restores a stale allow: it is a forward, authorized policy change with a new revision and audit record.

The signed deployment security-domain policy selects `request_boundary` or `commit_boundary`; a profile ID never selects disclosure semantics. `request_boundary` freshly authorizes and validates current revisions immediately before one composed finite response begins disclosure, permits that already-started response to finish across a later concurrent mutation, and denies every subsequent operation. `commit_boundary` adds the typed guard, egress-fence, lease/quiescence, and terminal-buffer proof defined by ADR-0005. Durable effect controls remain mandatory in both modes for streams, downloads, exports, print, credential issuance, provider mutations, direct-protocol calls, non-idempotent calls, operations that may outlive their logical request or job, long disclosures, and ambiguous external effects. On acceptance, ADR-0009's one closed bounded internal pagination/snapshot/verification/safe-idempotent-read plan uses one fresh centrally issued `ProviderAuthorizationScope`, one atomic single-holder execution claim, read-only per-call holder/scope/fence validation, and one closed logical audit without a separate durable permit transaction for each eligible read. The claim and scope cannot be shared, resumed, transferred, renewed, taken over, used after expiry/terminalization, or used to authorize an excluded effect or canonical acceptance.

Decision telemetry records decision ID, model/bundle/deployment-policy versions, selected disclosure mode, reason codes, latency, correlation, and cache behavior—never protected bodies or secrets. One composed `request_boundary` read produces one safe aggregate logical audit operation rather than per-row/panel/subquery writes. Audit records actor/requester/task/delegation and the decision metadata. Policy/model upgrades require signed/versioned bundles, migration tests, cache/projection invalidation, staged activation, and rollback to a compatible previously signed revision.
