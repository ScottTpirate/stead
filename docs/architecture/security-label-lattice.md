# Security-label lattice and container contract

Status: **Phase 0 baseline with pre-consumer corrections accepted by ADR-0002 and ADR-0006 at decision revision `24c74d52ef0a78840ab147da48c3d66589e49e3e`**
Requirements: `CLS-001`–`CLS-008`

The `SecurityLabel` fields are fixed in OWGP. A declarative security-label policy profile supplies the sensitivity vocabulary, handling regimes, categories/subcategories, compartments, dissemination controls, releasability, export controls, presentation rules, normalization, dominance, join, and lowering rules. Profiles are schema-validated and versioned source artifacts; the release pipeline MUST materialize and verify their signed activation material at `RG-08-SECURITY`. They are data, not executable plugins or a user-defined policy language. [ADR-0006](../adr/0006-signed-policy-bundle-distribution-and-activation.md) selects the exact activation-set signature profile. Phase 0 records the signing contract and does not fabricate a key ID, digest, or signature before a release candidate exists.

The checked-in `commercial` and `us_government` files are starter/reference profiles. Their stable identifiers carry no privileged semantics in Stead code, they are not product modes, and neither file claims exhaustive coverage of the environments suggested by its name. Any maintained profile that maps an external regulatory or classification regime MUST bind exact authoritative source snapshots and digests, mapped scope/version, mapping provenance, digest-bound tested coverage, and known limitations into signed activation material; a live URI alone is not provenance. Representability alone does not establish compliance, accreditation, authorization, or completeness.

Effective label is the least upper bound of source, explicit, container, and handling inputs under the selected profile. Sensitivity takes the profile maximum; restriction-valued handling, category, compartment, dissemination, and export coordinates compose by union; the allowed-audience `releasable_to` coordinate composes by intersection. An empty semantic permitted-audience intersection, or any contradictory, unknown, cross-profile, or otherwise unrepresentable result, denies. Empty restriction sets and an explicitly empty `releasable_to` input retain their profile-defined neutral meanings before composition. This audience-intersection wording is the project-owner-controlled pre-consumer correction accepted by [ADR-0002](../adr/0002-security-label-algebra-and-profile-identifiers.md), which supersedes the Phase 0 shorthand that grouped releasability with union-composed restrictions. No derivation can lower a source.

Repositories, tracker repositories, docs repositories, package namespaces, runner pools, caches, artifact stores, backup sets, and deployment domains are enforcement containers. Per-item markings cannot grant finer read access than a cloneable/provider container. Different access, classification, compartment, retention, or lifecycle requires a separate container.

Deployment security domains use [a machine-readable policy](../../policies/deployment-domains/domain-profile-v0.1.schema.json) whose profile-ID-keyed ceiling map makes duplicate/conflicting bindings structurally impossible and binds each permitted profile/version to its own applicable classification ceiling. The same policy fixes trusted identity/attribute authorities, integrations, notification channels, storage/encryption/residency, backup domains, runner pools/images, network egress, the closed `request_boundary` or `commit_boundary` disclosure/revocation mode, signing thresholds, key-custody separation, and cryptographic-assurance requirements. Inputs outside that declared domain deny. Cross-profile composition denies unless a future explicitly signed and approved compatibility/bridge contract names the exact source/target versions, direction, operation, mapping, trust binding, and non-weakening proof; it grants no data transfer or resource authority. The v0.1 contract rejects every non-empty bridge list. A label-profile ID never selects the disclosure mode.

Lowering/declassification/decontrol is denied by default, requires authority and written reason, is audited, invalidates caches/search/notifications/exports, triggers reconciliation, and uses the approval threshold and custody/separation controls required by the active deployment security-domain policy. Core Stead performs no cross-domain/write-down transfer.

Badges, banners, markings, and other classification presentation come from the active validated profile or its versioned system renderer; text and markings are authoritative and color is supplemental. Adding an approved profile requires no `stead-web` fork or profile-ID-specific authorization branch.

Profile upgrades run lattice property tests, full decision tables, signature verification, derived-resource recalculation, non-disclosure checks, and rollback rehearsal. Deployment-policy-controlled assurance features such as validated cryptographic modules, OSCAL evidence, and two-person controls do not by themselves establish compliance, accreditation, or authorization.
