## Decision and disclosure rules

Every protected request must apply the shared sequence:

```text
authenticated principal
→ principal type and, when present, initiating principal plus delegation/task scope
→ trusted attributes and session context
→ trusted runtime domain, profile-qualified classification ceilings, compartments, model-provider, tool-scope, and execution-environment context when applicable
→ canonical resource and effective security label
→ OpenFGA relationship/need-to-know decision
→ deterministic classification, handling, context, information-flow, and explicit-deny policy decision
→ provider/path enforcement
→ minimal audited decision metadata
→ allow or deny
```

An allow requires all applicable checks to allow and no deny to apply. An error, timeout, missing label, stale or expired attribute, unknown security domain, absent provider mapping, or unverifiable policy version fails closed. UI hiding is supplemental only.

For a future `agent` principal, the allow is additionally bounded by the intersection of delegating-principal authority, agent-specific authority, explicit task scope, runtime security-domain authorization, session/execution-environment restrictions, and resource classification/handling requirements. There is no broad inheritance of a human user’s permissions. Agent and task delegation are independently revocable. `service_account` is also a distinct principal type and is not an alias for a user or agent.

Unless policy explicitly permits existence-only disclosure, a denied principal must not learn a protected resource’s title, body, identifier, human key, path, owner, label, snippet, relationship, relationship count, result count, facet, suggestion, activity, notification text, package/artifact metadata, timing-distinguishable error, or existence.

### Status vocabulary

- `OPEN-P0/BLOCKING`: contract or implementation evidence is absent. The relevant milestone/release cannot pass.
- `CONTROL-DESIGNED`: Phase 0 contract is approved, but executable evidence is not complete.
- `TESTED`: the named automated test passes for the supported version/profile matrix; independent review is still pending.
- `VERIFIED`: independent QA/security reviewed evidence and accepted the stated residual risk.
- `EXCEPTION`: a narrowly scoped, expiring approval exists. Exceptions cannot authorize a known disclosure path, cross-domain transfer, or bypass of mandatory authorization.

## Common test fixture and oracle

All `SEC-BYP-*` tests use canonical resources in at least two organizations and two security domains, with labels spanning lower/higher sensitivity and compartment combinations. The principal matrix includes:

1. authorized relationship + sufficient label attributes + valid context;
2. sufficient label attributes but no project need-to-know;
3. project administrator without sufficient clearance;
4. equal sensitivity without the required compartment;
5. security officer permitted to administer metadata but not read content;
6. previously authorized principal whose attribute, membership, session, token, or provider grant is expired/revoked;
7. lower-classification runner and service principal;
8. principal/service from another organization or security domain.
9. `agent` with an explicit narrow task grant, its delegating user, an agent with only the user’s broader authority, a revoked task, a revoked agent, and a `service_account` control principal;
10. external runtime contexts varying security domain, profile-qualified classification ceilings, compartments, model provider, tool scope and execution environment.

The oracle records the OpenFGA model ID, policy-decision bundle/version and decision, effective security-label version, provider enforcement result, request/correlation ID, and expected audit record without placing protected content in evidence. Test fixtures use synthetic canary strings and keys so leakage scans can cover response bodies, headers, redirects, logs, events, caches, files and external sinks.

For agent vectors the oracle additionally records principal type, delegating/requesting principal, agent-specific grant version, task/resource/tool scope, revocation version, trusted runtime-context provenance, execution environment, and expected `requested_by`/`actor` attribution. It never logs prompts, model inputs/outputs, secrets, or protected bodies merely to prove the decision.

## Control synchronization and race requirements

A change that raises a label, removes a compartment, revokes a relationship, changes a security domain, expires an attribute, or adds an explicit deny must define one observable authorization boundary. After that boundary commits, no new protected content may be returned through a stale provider grant, token, object URL, cache, projection, notification, or replay. Implementations may choose a safe ordering—such as deny/version fencing before asynchronous cleanup—but cannot expose an eventual-consistency allow window. The precise ordering and rollback contract is an architecture-owned Phase 0 issue; changing the central authorization architecture requires an ADR.

## Closure and release use

A row advances to `TESTED` only when its automated negative and positive tests pass on every applicable supported installation/provider version. It advances to `VERIFIED` only after Workstream 13 independently reviews raw evidence and confirms the implementation owner did not self-approve. Evidence must link the requirement IDs, test run, build digest, provider versions, policy/model versions, fixture version, and any residual risk.

Any `OPEN-P0/BLOCKING` row that applies to a phase prevents that phase’s release. Any known unauthorized disclosure, direct provider path that exceeds central policy, or cross-domain/write-down path is an unconditional release failure under TEST-008. A waiver cannot convert such a failure to a pass.

AGENT-001–007 add compatibility and test seams, not a Phase 0 runtime. Phase 0 must not implement agent orchestration, prompting, model hosting, agent memory, `AgentRun` execution, A2A dispatch, a future Agent Registry, or the full MCP tool catalog. These rows become executable release gates only when their boundary is implemented later; Phase 0 approval requires the schema/model/policy/test contracts and explicit non-goal to be preserved.
