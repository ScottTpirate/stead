# ADR-0008: NATS stream, subject, retention, replay, ordering, and dead-letter contract

- **Status:** Proposed
- **Date:** 2026-08-30
- **Decision owners:** WS-07, with WS-01 architecture, WS-02 outbox/core, WS-06 security, WS-08 projection, and WS-12 operations review
- **Project-owner approval required:** no; this selects the JetStream mechanics deliberately left open by `ADR-CAND-006` without changing the locked event naming, transactional-outbox, authorization, classification, or deployment-domain decisions
- **Requirement IDs:** `EVT-001`, `EVT-002`, `EVT-003`, `EVT-004`, `ACT-001`, `NOTIF-001`, `AUD-001`, `AUD-002`, `CLS-006`, `TEST-005`, `PERF-002`, `PERF-003`, `PERF-004`
- **Affected contracts/modules/directories:** `/specs/asyncapi/`, `/packages/event-schemas/`, `/apps/worker/`, `/modules/audit/`, `/modules/notification/`, consumer-owned projection state, NATS deployment configuration, event/replay/security/performance tests, and operator backup/restore/upgrade evidence
- **Resolves on acceptance:** `ADR-CAND-006`
- **Supersedes / superseded by:** supersedes no accepted decision; a transport-subject prefix, cross-domain account export, different broker, global-order contract, or NATS-authoritative business state requires a superseding ADR

## Context and decision scope

The directive already fixes NATS JetStream, CloudEvents 1.0, AsyncAPI 3.1.x, the subject and event-type form `stead.<domain>.<action>.v<major>`, transactional outbox publication, at-least-once delivery, idempotent consumers, protected-content minimization, controlled replay, and the prohibition on global-order assumptions. PostgreSQL remains authoritative. [ADR-0005](./0005-authorization-and-policy-decision-topology.md) requires fresh authorization for protected delivery and durable-effect controls where an effect outlives an ordinary finite request. The PostgreSQL isolation decision for `ADR-CAND-002` owns the outbox and processed-event transaction seams.

This record selects only the Phase 1 broker partition, fixed stream classes, consumer behavior, resource ordering key, retention and capacity response, dead-letter representation, replay authorization, schema evolution, projection rebuild, and recovery mechanics. It does not define a domain event body, add an ontology concept, implement NATS, make events authorize an action, or make a consumer completion part of a request.

The design relies only on documented NATS operator/account JWTs with the built-in full resolver, JetStream accounts, limit-retention streams, explicit-ack durable consumers, publish deduplication, verified TLS, and server-side JetStream encryption at rest. Accounts are isolated subject namespaces; streams retain messages under explicit limits; durable consumers are stateful at-least-once views. The implementation must pin and support-test exact NATS server, client, and JWT/tooling versions before distribution. See the official NATS documentation for [operator mode](https://docs.nats.io/running-a-nats-service/configuration/securing_nats/auth_intro/jwt), [accounts](https://docs.nats.io/running-a-nats-service/configuration/securing_nats/accounts), [streams](https://docs.nats.io/nats-concepts/jetstream/streams), [consumers](https://docs.nats.io/nats-concepts/jetstream/consumers), and [TLS plus JetStream encryption at rest](https://docs.nats.io/running-a-nats-service/configuration/securing_nats/tls).

## Decision drivers

- Preserve the locked NATS subject form without exposing organization or security-domain identifiers in subjects.
- Prevent a credential or subject-ACL error in one Organization or security domain from becoming a cross-tenant subscription.
- Keep authoritative requests independent from NATS availability while retaining every unacknowledged outbox intent.
- Make duplicates, out-of-order delivery, restart, poison messages, and replay normal tested states rather than exceptional assumptions.
- Keep projection rebuild possible after the JetStream retention window from authoritative owner snapshots plus retained incremental events.
- Bound storage, message size, retry, concurrency, and operator actions without silently discarding acknowledged authoritative mutations.
- Preserve payload minimization and existence nondisclosure in events, broker administration, telemetry, dead-letter records, and replay.
- Ensure a process crash at every attempted delivery cannot exhaust broker delivery and strand a source message without a durable terminal outcome.
- Close every account, stream, and consumer setting against the exact pinned NATS version so a permissive default or newly introduced field cannot add a loss or disclosure path.
- Require authenticated encryption in transit and at rest without making transport credentials or encryption keys product authority.

## Considered options

1. **One isolated NATS account for each `(security_domain_id, organization_id)` pair; the locked subjects inside it; four non-overlapping limit-retention stream classes; durable pull consumers; PostgreSQL idempotency and controlled exact-message replay.** This preserves the subject contract, provides an enforceable organization/domain broker boundary, and keeps one simple event model. It adds account lifecycle and per-partition connection management. Accepted.
2. **Status quo: leave account, stream, retention, ordering, and replay mechanics deferred.** This leaves `STEAD-P1-007` unable to implement subject authorization, deterministic recovery, or `TEST-005`. Rejected.
3. **One shared account and subjects prefixed with security-domain and Organization tokens.** This partitions efficiently but changes the locked `stead.<domain>.<action>.v<major>` NATS address and exposes tenant-routing tokens to every credential that can observe the namespace. Rejected for Phase 1.
4. **One account per deployment security domain and payload-only Organization routing.** NATS permissions and stream filters cannot enforce a value inside a JSON payload. A subscriber allowed on a subject could receive other Organizations in that domain. Rejected.
5. **One global stream or a stream per domain with consumer-side filtering.** This makes stream credentials and mistakes cross-domain/cross-Organization disclosure paths and couples unrelated retention and recovery. Rejected.
6. **Work-queue or interest retention for canonical events.** Acknowledgment or consumer deletion could remove the only retained transport copy before another projection or replay needs it. Rejected; independent durable consumers use limit retention.
7. **Treat stream order, publish deduplication, or exactly-once acknowledgments as sufficient correctness.** Publisher retries can outlive the duplicate window and consumer acknowledgments can be lost. Rejected; consumer-owned state is idempotent and out-of-order safe.
8. **Copy full failed payloads and stack traces into a dead-letter stream, then let operators republish them.** This duplicates protected data, turns broker possession into apparent authority, and can repeat effects across consumers. Rejected.
9. **Use finite `MaxDeliver` and a max-delivery advisory as the terminal trigger.** A process can crash before every PostgreSQL attempt/failure transaction and exhaust the broker counter; an advisory is not the owner transaction that makes terminal evidence and outbox intents atomic. Rejected; unlimited broker redelivery plus a bounded owner attempt state machine cannot strand the source at that boundary.
10. **Rely on network placement, encryption without peer verification, or volume encryption alone.** Each leaves a different client/route/restore or store path unauthenticated and makes profile behavior deployment-specific. Rejected; every production NATS link uses verified TLS and JetStream storage uses a deployment-domain-bound SecretProvider key, with authenticated backup protection layered separately.
11. **Validate only selected manifest fields and accept NATS defaults or newly introduced fields.** A dependency upgrade could silently enable asynchronous persistence, republish, mirrors/sources, transforms, rollup, TTL, direct reads, or no-ack behavior. Rejected; the exact pinned-version account, stream, consumer, ACL, TLS, and encryption read-back is closed.
12. **Use a host, deployment, account, partition, or binary URL as CloudEvent `source`.** Restore or producer replacement would change semantic idempotency identity and could repeat a durable effect. Rejected; each AsyncAPI channel owns one restore-stable logical producer URN.

## Decision

### Organization and security-domain partition

Every event-ready Organization has exactly one event partition for its current deployment security domain. A partition is one operator-issued NATS account identified by an opaque account public key and an authorized PostgreSQL mapping to `(organization_id, security_domain_id, partition_generation)`. That mapping and its requested/provisioning/ready/failed delivery state live behind the WS-02-owned `core_outbox` delivery repository port already granted to the WS-07 publisher; this ADR creates no eventing schema and grants WS-07 no direct `core_outbox` table access. WS-07 owns the partition manifest and provisioning behavior through that typed port. Account, stream, durable-consumer, credential, and metric names contain only bounded opaque identifiers; the canonical Organization and security-domain identifiers remain in the schema-validated CloudEvent data and access-controlled Stead state. An Organization whose partition is requested or degraded remains authoritative Stead state, but its outbox records remain pending and its asynchronous activity/inbox/search state reports one safe non-resource-specific degraded condition until provisioning succeeds.

Subjects inside every partition remain exactly the AsyncAPI addresses shaped as `stead.<domain>.<action>.v<major>`. No Organization, Team, Project, label profile, classification value, security domain, deployment profile, or provider token is added to a subject. CloudEvent `type` uses the same required form, and CloudEvent `subject` must equal the canonical resource URI in `data.resource.uri`.

Phase 1 creates no account imports or exports for protected event subjects. A worker credential is scoped to one partition and one registered role: outbox publisher, named consumer, dead-letter recorder, replay executor, or bounded observer. It receives only the exact publish, consumer, and JetStream API permissions that role needs. Ordinary API credentials, browser sessions, provider credentials, and human operator sessions receive no NATS credential. Broker provisioning credentials are separate from ordinary relay/consumer credentials and are not mounted in those runtimes.

Partition provisioning is asynchronous and idempotent. Authoritative Organization creation commits PostgreSQL state plus its ordinary outbox intent; it never waits for NATS and does not create a second database-then-broker job. When the relay claims that still-pending row and finds no ready mapping, it hands the tuple and declarative manifest to the typed partition provisioner before attempting publication. The provisioner transitions requested/provisioning/ready or failed generation state only through the reviewed WS-02 delivery repository port, creates or verifies the account and streams outside every PostgreSQL transaction, and returns only after a read-back verifies the exact account JWT, limits, subjects, replicas, and permissions. The same outbox row remains pending across a crash and becomes publishable only after the mapping is ready. A mismatched account mapping, reused account key, security-domain change, capacity refusal, or nonconforming stream fails closed without losing or falsely completing the row. Moving an Organization between security domains is not an in-product event-account migration and cannot create a cross-domain transfer path.

Organization deletion atomically appends its final tombstone event intent and places the mapping in `draining` with that exact outbox fence. The relay may publish only already-committed intents through the fence, including the tombstone, and changes the mapping to `tombstoned` only after every intent through the fence has a verified publish acknowledgment or an authorized authoritative rebuild has superseded it. No post-fence intent is admitted. An unavailable partition leaves the tombstone pending while ordinary reads and projections independently suppress deleted state from current authority; it never reopens publication or exposes stale existence. Tombstoning does not immediately remove streams, dead-letter evidence, resolver claims, or recovery state. Authorized retention completion, proof that the fence is drained or superseded, and backup evidence precede an audited purge. Local, external, Kubernetes, and air-gapped profiles use the same logical partition contract.

### Provisioning authority, capacity, and connections

Phase 1 uses NATS operator mode with the built-in full resolver; it does not silently fall back to the global account, static shared credentials, an authentication callout, or cross-account exports. The NATS servers receive only the installation operator's public trust material and resolver state. A dedicated provisioning controller obtains a delegated operator account-signing key by reference from the approved `SecretProvider`; that key is never mounted into the API, relay, consumer, browser, or ordinary worker roles. For each partition generation the controller creates an account key, an account JWT with the exact JetStream limits and no imports/exports, a per-account signing key, and distinct role-scoped user JWTs.

Signing a claim does not install it. The controller separately obtains a restricted system-account resolver-publication credential from the `SecretProvider`. It may publish only a properly operator-signed claim to `$SYS.REQ.ACCOUNT.<account-public-key>.CLAIMS.UPDATE`, perform the corresponding exact-account `CLAIMS.LOOKUP`, and receive replies on its bounded inbox; it has no general system-account, monitoring, stream, subject, or account-delete permission. The public key in the request subject, the claim subject, expected issuer epoch, signed bytes, and requested mapping must agree. After resolver read-back, the controller uses a separate, generation-scoped account-provisioner user credential whose permissions are limited to creating and inspecting that account's registered stream and consumer manifest; it cannot publish domain events, consume them, access another account, or use unrestricted JetStream administration. A generation becomes ready only after independent resolver and JetStream read-back matches the registered digests and limits. PostgreSQL stores only public keys, JWT and manifest digests, signing-key epochs, revocation status, and secret references. Operator, system-account, account, signing, and user seeds or bearer credentials never enter PostgreSQL, events, logs, metrics, backups, or release evidence.

User credentials rotate inside one account generation. Account-key reuse, an account-signing-key change, security-domain movement, or loss/compromise of account authority creates a new partition generation. NATS account identities are not described as revocable: the controller instead publishes a newer operator-signed old-account claim with zero allowed connections, removes or revokes every old user/signing authority, verifies that active connections close, and keeps the no-import/no-export claim tombstoned in the resolver until its audited retention/purge gate. The new account never imports from or exports to the old one.

Operator signing-key rotation is an installation-owner operation, not a controller privilege. The provisioning controller never holds the operator identity seed and cannot alter the operator JWT or its trusted signing-key set. An explicitly bounded ceremony uses the offline installation operator identity authority to add the successor public signing key, deploy and verify that operator JWT on every server, make the successor secret reference available, reissue and resolver-read-back every active account claim, then remove the predecessor public key in a new operator JWT and verify server-wide reload before destroying the predecessor secret. Missing, ambiguous, expired, partially deployed, or unverifiable operator/account issuer state leaves provisioning and publication denied. The exact server/JWT dependency, secret implementation, key algorithm, validity window, resolver configuration, system-account ACL, rotation ceremony, and compromise response require dependency/security approval in `STEAD-P1-007`; this ADR authorizes no package or secret value.

### Production transport, at-rest protection, and closed manifests

Every production NATS path uses authenticated, verified TLS with no plaintext listener, reconnect, advertised-address, or protocol fallback. The client listener, including the provisioning controller's resolver update/lookup traffic and every relay, consumer, replay, maintenance, observer, and system-account connection, requires client certificates and validates the server certificate chain, name, validity, and intended use; NKey/JWT role credentials remain independently required and a TLS identity never becomes product authority. The production client listener uses TLS-first handshakes with fallback disabled. Every enabled cluster route, gateway, and leaf-node link uses its own mutually authenticated TLS block, verifies both peers, and uses certificates valid for both server and client authentication. Phase 1 disables WebSocket, MQTT, leaf-node, gateway, and unauthenticated monitoring listeners unless a reviewed deployment profile explicitly needs one and applies an equal or stronger authenticated-TLS and authorization contract. Missing trust roots, hostname mismatch, expiry, wrong key usage, partial certificate rotation, or any plaintext endpoint leaves the node unready and all event publication/consumption denied.

JetStream file storage is encrypted at rest with the NATS server's authenticated-encryption facility. Its server-wide key comes only from an approved `SecretProvider` reference bound to the installation ID, deployment security-domain policy revision, NATS cluster identity, and store generation; the key value never appears in configuration source, PostgreSQL, events, logs, metrics, snapshots, backups, or release evidence. Rotation performs one controlled restart with the successor as current key and predecessor as transitional previous key, verifies stream/consumer read-back plus old/new encrypted-store and authenticated-backup restore, then removes the previous-key reference and restarts again before retiring the predecessor. A missing, wrong, revoked, cross-domain, or stale key reference cannot initialize or restore JetStream. Any JetStream snapshot entering backup is protected by the deployment's authenticated-encryption backup set and same-domain/non-weaker restore checks; server-side at-rest encryption is not presumed to encrypt exported snapshot material.

The only admitted broker shape is canonical `stead.nats.partition-manifest.v1`. It binds exact dependency-approved NATS server, client, and JWT/tooling versions; the complete operator/account claim bytes and digests; production TLS and at-rest settings; four stream configs; every durable consumer config; role ACLs; and the expected complete read-back field set for that pinned server. Its JSON schemas reject unknown properties. The controller compares canonical values, not a permissive subset: a field added by a server upgrade, an omitted field that would take a server default, a duplicate/alias representation, or any read-back difference leaves the generation unready until a reviewed manifest-version migration explicitly classifies the field.

The account claim is also closed: zero imports and exports; JetStream enabled; memory storage limit exactly zero; file storage limit exactly the four stream maxima plus 25 percent headroom; exactly four streams; at most 144 consumers; finite positive account-wide connection, subscription, payload, and data-rate limits; and account/stream `MaxAckPending` no greater than 256. The local profile's account-wide connection ceiling is 64 in addition to the existing per-worker-role ceiling of 16. A deployment may lower connection, subscription, payload, or data-rate ceilings only when the scale fixture still passes, and may raise them only through explicit effective configuration and capacity/security preflight; unbounded values are invalid.

Every stream read-back must match its table row and the following closed values: `LimitsPolicy`, `FileStorage`, `DiscardNew`, synchronous/default persistence (never asynchronous persistence), `no_ack=false`, no mirror, no sources, no subject transform, no republish, no placement outside the declared same-domain cluster, no rollup, no per-message TTL or subject-delete-marker TTL, no direct or mirror-direct access, no first-sequence override, no per-subject discard mode, no atomic/batched publishing, no counter or scheduled-message mode, and no unregistered metadata. `sealed` remains false because controlled retention and recovery need maintenance; delete and purge are instead denied by runtime ACL. A separately mounted maintenance credential may update an exact registered manifest or purge/delete only after the tombstone/retention/backup authorization gate. It cannot publish, consume, replay, or cross accounts and is never mounted in relay, handler, replay, or provisioner runtimes.

Every consumer is a named durable pull consumer with explicit acknowledgment, an exact registered filter set and checkpoint/start policy, instant replay policy, no push subject, no headers-only mode, no direct mode, no flow control, no sampling, no rate-limit override, matching replica policy, `MaxAckPending<=256`, `MaxRequestBatch<=128`, `MaxRequestMaxBytes<=1 MiB`, `MaxRequestExpires<=250 ms`, and the redelivery contract below. Runtime consumer credentials may fetch and acknowledge only their registered durable; they cannot create, update, delete, pause, or reset it. Provisioning, startup, reconnect, restore, and periodic doctor checks all compare account, stream, consumer, ACL, TLS, encryption-reference, and dependency-version read-back to the manifest digest before a runtime binds.

Every deployment manifest declares `max_ready_event_partitions`, `max_partition_connections_per_worker_role`, `max_partition_connections_total`, replica count, and usable JetStream file capacity. The Phase 1 local profile defaults to four ready partitions, one replica, at most sixteen simultaneous partition connections per worker role, and at most 64 total connections in one partition account. Larger values require explicit effective configuration and preflight evidence; zero/unbounded values are invalid. With the table below, logical stream maxima total 2 GiB per partition and the required 25 percent recovery headroom makes the minimum usable capacity `max_ready_event_partitions × 2.5 GiB × replicas`, in addition to current non-JetStream use and operator reserve. `steadctl` preflight and doctor verify that arithmetic before provisioning and continuously compare declared capacity, filesystem free space, actual stream use, and pending outbox age. A deployment at its ready-partition ceiling queues further mappings in requested state rather than overcommitting NATS or dropping an outbox row; an operator must increase verified capacity or retire an eligible tombstoned generation.

Connections are lazy and scheduler-bounded, never one permanently hot connection for every account/durable pair. Each process role uses only its own per-partition credential, multiplexes the permitted durables within that account where the client contract allows, closes idle connections, and services ready partitions with a fair checkpointed scheduler under the declared global connection ceiling. Durable state remains on the server while disconnected. The standard scale fixture runs at the declared partition and durable ceiling and must meet lag targets without exceeding connection, goroutine, file-descriptor, fetch-loop, memory, or credential-cache bounds.

### Fixed stream classes

Each partition contains these non-overlapping file-backed JetStream streams. Names carry the opaque partition generation and class, never canonical tenant data.

| Stream class | Subject families | `MaxAge` | `MaxBytes` | `MaxMsgs` | `MaxConsumers` | Purpose |
|---|---|---:|---:|---:|---:|---|
| `domain_v1` | organization, project, workitem, comment, document, scm, ci, artifact, attachment, storage | 30 days | 1 GiB | 5,000,000 | 64 | authoritative-change transport and ordinary projection replay |
| `control_v1` | identity, authorization, classification, audit, migration, operations | 90 days | 512 MiB | 2,000,000 | 32 | security/control and operator lifecycle transport |
| `projection_v1` | search_graph, notification | 14 days | 256 MiB | 1,000,000 | 32 | rebuildable projection lifecycle and notification-state transport |
| `dead_letter_v1` | dead_letter | 90 days | 256 MiB | 250,000 | 16 | minimized controlled-failure and replay lifecycle records |

Every stream uses `LimitsPolicy`, `FileStorage`, `DiscardNew`, the table limits, a 64 KiB maximum including headers, and a 24-hour duplicate window. The account file-storage limit must equal or exceed the sum of its stream byte limits plus 25 percent recovery headroom, and the effective server/volume/replica capacity must satisfy the declared ready-partition formula above without overcommit. Runtime identities cannot delete or purge streams. Local mode uses one replica; a declared clustered availability profile uses three. Availability and capacity profile selection never depends on a security-label profile ID.

`DiscardNew` is deliberate: capacity pressure rejects the JetStream publish rather than evicting an unexpired event. The relay keeps the PostgreSQL outbox record pending, backs off, and alerts. Max-age expiry remains expected transport retention, not deletion of authoritative state. A deployment policy may require longer ages or larger capacities; it may not silently reduce these Phase 1 release minima. Retention changes are manifest-versioned and preflighted against current consumer lag and rollback windows.

The relay publishes only a schema-validated event to the one stream class registered for its AsyncAPI channel, sets `Nats-Msg-Id` to the immutable CloudEvent `id`, requires a JetStream publish acknowledgment for the expected stream, and records the acknowledged account, stream, and sequence before marking the outbox delivery complete. A lost acknowledgment may cause a duplicate. No correctness claim depends on the 24-hour server duplicate window.

### Consumers, idempotency, and resource ordering

Production handlers bind durable pull consumers with `AckExplicit`, one fetch loop per durable, at most 128 messages or 1 MiB per fetch, a 250 ms fetch expiry, `MaxAckPending` no greater than 256, and `MaxDeliver=-1`. The broker therefore continues redelivery until Stead has durably acknowledged either success or a terminal outcome; it can never strand a message merely because a process crashed through a finite broker counter. The Phase 1 consumer manifest sets `BackOff=[1s, 5s, 30s, 2m, 10m, 30m, 2h, 12h]`; with unlimited delivery the pinned-server contract repeats the final delay after this list. Compatibility tests establish the exact attempt/timing behavior. `BackOff` governs acknowledgment timeout, so handlers either allow that timeout or use an explicit delayed negative acknowledgment matching the registered next delay; an immediate/plain negative acknowledgment is prohibited. Max-delivery advisories are not a terminal trigger or correctness input.

Stead, not NATS, owns the finite handler-attempt budget of eight. Before domain handling, the consumer opens a short owner transaction keyed by `(consumer_contract_id, partition_generation, source_stream, source_sequence)`, locks or creates its delivery-attempt row, first returns an already committed processed or terminal result without increment, and otherwise commits the next bounded attempt plus safe timestamps. Attempts one through eight may enter the ordinary handler. On the next delivery after attempt eight, or immediately for a deterministic permanent schema/authorization/partition/integrity result, that same owner transaction moves the row to terminal and atomically appends the minimized dead-letter and audit intents; only then may the source message be acknowledged. A crash before the attempt transaction leaves the message broker-eligible without consuming a durable attempt. A crash after an attempt commit consumes that attempt and redelivers. A crash after a successful handler transaction is recognized as processed before any later increment, and a crash after the terminal transaction is harmless through the terminal row and outbox idempotency. Thus a crash at every handler attempt reaches a durable terminal boundary on recovery, while a process that never reaches PostgreSQL cannot exhaust broker delivery or falsely claim a terminal result. Replay is immediate but backpressured by the same batch, acknowledgment, database, attempt, and authorization limits.

The resource ordering key is the validated pair `(CloudEvent source, CloudEvent subject)`, where subject is the canonical resource URI. `source` is not a deployment URL or process identity: AsyncAPI registers exactly one restore-stable logical producer source for every channel, shaped `urn:stead:producer:<event-family>`, with the family equal to the first domain token in that channel's locked address. It contains no installation, hostname, account, partition, security-domain, replica, binary, or version value. The relay rejects any emitter-supplied or persisted source that differs from the exact channel registry value, and restore, producer replacement, topology migration, and dual-major publication reuse the same logical source. Dispatchers may serialize or consistently lane this key for efficiency, but correctness must survive duplicates and any delivery order. No consumer assumes global order, cross-stream order, wall-clock order, or an order between two resources. A consumer of an authoritative change treats the event as an invalidation/reference, not an unversioned authoritative delta: it obtains current owner state or applies an owner-supplied version/fence before a conditional projection update. Deletes use tombstones. Reverse-order and concurrent-delivery tests must converge on current authoritative state.

Each durable consumer contract has an owner-controlled PostgreSQL processed-event table. Its transport-duplicate identity is `(consumer_contract_id, partition_generation, cloud_event_id)`; source stream/sequence, payload digest, schema identity, closed processing-result code, and checkpoint are evidence stored under that identity, not extra uniqueness that could admit the same message twice. Its semantic-effect identity is exactly `(consumer_contract_id, organization_id, cloud_event_source, semantic_event_family, data.idempotency_key)`, where `cloud_event_source` must be the restore-stable AsyncAPI registry value above. The digest of the consumer's canonical normalized operation is evidence stored under that identity and must match on reuse; it is deliberately not part of the uniqueness key. `semantic_event_family` is the registered compatibility group with the serialized major removed; it is never caller supplied. Partition generation, deployment, host, process, and security domain are deliberately absent so account rotation, authority recovery, restore, producer replacement, and a reviewed compatibility transition cannot reapply an effect. In one owner transaction, the handler performs its conditional projection/state change, records both identities and their evidence, and appends any required audit/outbox intent. It acknowledges NATS only after commit. A repeated CloudEvent ID with the same bytes is skipped and acknowledged; the same ID with different bytes is quarantined. A repeated semantic key with an equivalent normalized operation is also skipped, including after restore, producer replacement, partition-generation replacement, and dual-major delivery; the same semantic key with a different normalized operation or non-registry source is quarantined before any effect.

One logical event intent from an authoritative mutation has one stable data `idempotency_key` across partition generations and every compatibility representation. Separate logical event intents produced by one mutation use distinct keys. Each serialized event major has its own CloudEvent `id` and payload digest, so two different representations never masquerade as a transport redelivery. During a dual-major window, consumers declare one compatibility group, normalize supported majors to the same semantic operation, and use the semantic-effect identity before any projection change or durable effect. Unsupported consumers remain on one major and cannot receive both. These rules, not stream placement or timing, prevent a logical effect from being applied twice.

External notification, provider, credential, export, or other durable effects reauthorize current resource/container/domain/label state and use the ADR-0005 durable effect-permit and downstream idempotency contract. Event possession, prior authorization metadata, a broker credential, a replay approval, or a processed-event row never grants authority. Denied or stale events produce no existence-leaking notification, count, activity, delivery, or diagnostic.

### Schema and payload enforcement

The relay and every consumer validate the CloudEvents envelope, registered type/channel relationship, exact allowed `dataschema` identity/digest, shared event data, account mapping, Organization, security domain, canonical subject/resource equality, and maximum size before use. The account tuple and payload tuple must agree. Unknown fields rejected by the registered schema, an unknown schema, unsupported major, invalid event-type/channel pair, malformed actor context, missing idempotency key, or payload above 64 KiB cannot reach a domain handler.

Events contain only canonical identifiers/references, the closed effective-label reference defined below, safe actor/correlation/causation context, changed-field names, and bounded lifecycle metadata. They contain no protected body, comment/document text, prompt, memory, credential, token, signature material, provider locator, source code, attachment bytes, arbitrary exception text, or stack trace. Error classes and change fields come from closed registries.

The required `effective_security_label` event member is a minimized reference, not the resource's `SecurityLabelValue` and not presentation data. Before the first producer is admitted, the WS-07-owned shared event schema must make it an `EffectiveSecurityLabelEventRef` with exactly four required string members and `additionalProperties: false`: `profile_id` matching `^[a-z][a-z0-9_]{0,63}$`; `profile_version` matching the active profile's `^[0-9]+\.[0-9]+\.[0-9]+$`; `policy_bundle_id` matching `^sha256:[0-9a-f]{64}$`; and opaque `label_revision` matching `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`. The tuple identifies the policy/profile semantics and authoritative effective-label revision that a consumer must refetch through the owning resource port and recheck under current authorization. It is not an allow decision, and account/Organization/security-domain routing never depends on a label value. The current foundation schema's full `SecurityLabelValue` reference is a pre-producer placeholder and must be replaced by this closed reference in the WS-07 schema/compatibility contribution; because no runtime producer has been admitted, this correction creates no dual-publish or persisted-event migration claim.

No other label material is permitted in an event. Forbidden raw label material includes sensitivity values, handling regimes, categories, compartments, dissemination or releasability values, originator/export/derivation/authority/review fields, or a digest/copy of their normalized value. Forbidden display material includes markings, banners, warning text/actions, colors, renderer identifiers, and other `SecurityPresentation` fields. Forbidden provider material includes provider label/tag names or IDs, paths, locators, and source metadata. A dead-letter event carries only the containing Organization's own current `EffectiveSecurityLabelEventRef` required by its canonical envelope; it never copies the failed resource's reference or any failed-event label material. Event payload validation rejects a missing, malformed, or extra label-reference member.

Within one subject major, schema evolution is additive and backward compatible: an existing field cannot be removed, narrowed, reinterpreted, or made newly required for an already admitted producer. Consumers declare an exact supported schema set and digest. A breaking change creates a new subject/type/schema major and an explicit coexistence plan; it is never accepted by best-effort parsing. AsyncAPI plus referenced JSON Schemas is the sole channel/type/schema registry, and compatibility fixtures validate every producer and consumer before activation.

### Dead-letter and poison-message handling

Dead-letter records use `stead.dead_letter.recorded.v1` in the failing event's same account. The dead-letter CloudEvent's own `subject` and `data.resource.uri` both identify the containing canonical Organization; the failed event's subject remains digest-only. The event contains only that required canonical envelope context plus opaque partition generation, source stream class and sequence, digests of the source event ID/subject/payload/schema, consumer contract ID, attempt count and first/last/terminal timestamps, one closed failure code, retryability, correlation/causation digests, and an opaque authorized replay-request reference when applicable. It never embeds the source event type or source logical producer when those are derivable from the registered stream/consumer contract, and it never embeds the original payload, parser input, exception message or digest, stack trace, credential, actor/resource identifier, canonical failed-resource URI, label reference, or protected body.

The failure-code registry is exactly `schema_invalid`, `schema_unsupported`, `account_binding_mismatch`, `payload_integrity_mismatch`, `authorization_denied`, `effect_fence_stale`, `handler_retryable`, `handler_terminal`, `attempt_budget_exhausted`, and `internal_redacted`. Retryability is exactly `retryable` or `terminal`; unknown internal errors map to `internal_redacted`, never to caller/server text. The owner delivery-attempt, processed-event, terminal-failure, audit-intent, and dead-letter-intent rows use closed schemas containing only the transport/semantic keys needed for idempotency, the safe values above, normalized-operation digest when applicable, bounded counters/timestamps, and opaque safe references. Arbitrary maps, JSON error blobs, raw NATS metadata, exception strings/digests, resource titles/URIs, actor/provider data, or copied payload fields are prohibited in PostgreSQL as well as in events, telemetry, doctor/support output, and backup manifests.

Before terminating or acknowledging a permanently failed delivery, the consumer atomically records its owner terminal state and dead-letter/audit intents in PostgreSQL through the attempt state machine above. NATS max-delivery advisories are optional safe observability signals only, never the reliable trigger. Failure while processing a dead-letter lifecycle event records only `internal_redacted`, bounded counters/timestamps, and an alert; it does not recursively dead-letter the dead-letter event. Owner tables and authenticated backup/restore fixtures carry protected-value canaries and prove none can reach attempt, processed, failure, outbox, dead-letter, audit, snapshot, backup-manifest, restore-diagnostic, or support-evidence fields.

The original event remains in its source limit-retention stream until ordinary expiry. A dead-letter record is not authority and is not a copy of recoverable data. If its source event expires, the only recovery is an owner-authorized authoritative snapshot/projection rebuild or a new domain operation; the platform never fabricates the missing event.

### Authorized replay and projection rebuild

Replay is requested only through a Stead API/operator operation protected by central authentication, OpenFGA, deterministic policy, profile-qualified ceiling, current provider/path and revision/fence checks, and audit. The request binds one partition generation, consumer contract, source stream and sequence/event ID, expected payload/schema digests, bounded range or exact ID set, purpose, expiry, requester/actor, and maximum work. It cannot cross an account, Organization, security domain, consumer contract, or schema allowlist.

The replay worker rechecks the approval and current security state, retrieves the exact retained source message, verifies every binding, and invokes the same schema validation, authorization, idempotency, transaction, and effect-permit path as ordinary delivery. It does not republish the event to all consumers and cannot override a completed processed-event row without a separately authorized repair operation. Replay success/failure and resulting checkpoint are audited without payload content.

A projection rebuild uses a consumer-owner build generation: establish an authorized owner snapshot/checkpoint, load current canonical state through typed owner ports in bounded batches, validate and atomically switch the rebuilt generation, then consume retained events after the checkpoint. Events remain incremental transport, not the snapshot system of record. Unknown lag, a gap before the retained start, mismatched account generation, invalid schema, or stale authorization suppresses the projection until a safe rebuild completes. Search/activity/inbox counts never reveal suppressed rows.

### Observability, backup, and performance

Safe metrics cover outbox commit-to-publish acknowledgment, publish-to-consumer start, handler transaction, event-to-visible p50/p95/p99, bounded batch sizes, pending and age lag, broker redelivery, durable attempt and terminal counts, duplicate/collision, schema rejection, capacity rejection, dead-letter, replay, rebuild, certificate/key-reference expiry state, manifest drift, and checkpoint age. Normal metric labels are low-cardinality stream class, consumer contract, closed result class, and deployment mode. Per-partition diagnostics require authorized drill-down and use opaque partition IDs. Logs, traces, metrics, doctor output, and support evidence never record an event payload; canonical resource titles; any member of `EffectiveSecurityLabelEventRef`; raw, display, or provider label material; credentials; raw TLS/NATS errors; or arbitrary processing errors.

Authoritative requests perform zero NATS operations and wait for zero relay/consumer acknowledgments. Relay and consumer work is bounded and batched; handlers use set-oriented authorization and database operations rather than per-row waterfalls. The standard fixture must demonstrate event-to-visible p95 at or below one second and the five-second release ceiling, plus stable SQL/write/OpenFGA/provider counts as batch cardinality grows.

Backup/restore treats JetStream as reconstructible transport. The required backup contains PostgreSQL authoritative state, pending outbox, minimized processed/attempt/terminal/checkpoint state, the logical-producer-source registry, declarative opaque operator-public/account/stream/consumer manifests, issuer and signing epochs, and secret-reference metadata; it contains no operator, system-account, account, signing, user, TLS-private, or JetStream-encryption key. The deployment's configured SecretProvider backs up or reprovisions secret values under its own approved procedure. If the exact issuer/account or at-rest authority cannot be recovered and verified, restore creates a fresh partition generation and store generation, leaves the unrecoverable old generation quarantined/tombstoned rather than claiming NATS account revocation, drains pending outbox, and rebuilds projections from authoritative snapshots; it never attaches the new generation to an old account or trusts an old JetStream snapshot. A compatible, authority-matched, authenticated-encrypted JetStream snapshot may accelerate restore but never replaces those sources. Restore verifies deployment-domain/installation/cluster key-reference binding, TLS on every enabled link, operator trust deployment, resolver update/lookup behavior, JWT issuers/digests, stable logical producer sources, zero-connection tombstones, exact closed manifest/ACL read-back, capacity, and credentials before publication, then performs outbox drain and snapshot-plus-incremental projection rebuild tests before readiness. Air-gapped operation uses the same embedded resolver and declarative state with no external broker control plane.

## Consequences

- Organization and security-domain isolation is enforceable without changing or leaking through the locked subject form.
- Phase 1 pays a bounded account-lifecycle and credential-management cost per Organization/domain pair; later scale evidence may justify a superseding partition ADR.
- Limit retention and `DiscardNew` favor visible backpressure and recoverable outbox lag over silent eviction.
- JetStream publish deduplication reduces common duplicates but PostgreSQL processed-event state remains the correctness boundary.
- Unlimited broker redelivery is intentionally paired with a finite PostgreSQL handler-attempt budget; poison messages consume bounded handler work and can never disappear at a broker-only terminal edge.
- Production requires certificates and one server-wide JetStream encryption key per installation/security-domain-bound store; rotation, backup, and recovery gain explicit operational ceremonies.
- Exact-version manifest closure makes dependency upgrades intentionally fail closed until every newly exposed field is classified and tested.
- Replays are consumer-specific, authorized, digest-bound, and idempotent; broker operators cannot turn message possession into product authority.
- Projection rebuild remains possible after stream expiry because authoritative owner snapshots, not indefinite broker history, define current state.
- No NATS backup or stream sequence is described as authoritative business data.

## Rollout and supersession

1. Accept this decision at one immutable revision with every named non-author review; keep dependent implementation blocked until then.
2. In parallel before NATS implementation, land the WS-02-owned partition-generation/draining migration and port contribution, each consumer owner's minimized attempt/terminal-state contribution, the WS-07-owned AsyncAPI logical-source/header/data contracts and compatibility/negative fixtures, and the early WS-12-owned versioned deployment-config/Compose/TLS/encryption-reference/preflight child. The early child depends only on the accepted ADR and its own foundation prerequisites; it is not full `STEAD-P1-011` completion and creates no dependency from that parent back to `STEAD-P1-007`.
3. Pin and dependency-approve the exact NATS server/client/JWT versions; generate the complete `stead.nats.partition-manifest.v1` allowlist from that version; provision verified TLS, encrypted file storage, declared accounts and four streams; read back every field; then start schema-validating consumers from an explicit checkpoint before enabling outbox relay.
4. Enable relay with publish acknowledgments and compare outbox, stream, consumer, and processed-event checkpoints; no request path changes.
5. Exercise plaintext and wrong-certificate denial, at-rest key rotation/wrong-key/restore, unknown/unsafe manifest fields, capacity failure, crash at every delivery/terminal boundary, poison, replay, NATS-total-loss, snapshot rebuild, backup/restore canaries, and version rollback before promotion.
6. For a new event major, create new subjects and update the versioned stream manifest. The `_v1` stream-class suffix is the manifest contract version, not an event-type major; a reviewed migration may add the new subject to the existing class or create a parallel class when retention/rollback isolation requires it. Deploy compatibility-group consumers first and dual-publish only when the reviewed migration explicitly requires it. Remove the old subject/stream binding only after semantic-idempotency evidence, all consumers, replays, rollback windows, and retained outbox records prove safe.

Manifest evolution is expand/coexist/contract. A successor first admits only fields classified by an exact-version schema and read-back fixture, preserves stable logical producer sources and semantic keys, rolls TLS/encryption references through an overlap that never enables plaintext, and keeps both consumer/result/failure schemas readable through the rollback window. A server or client upgrade that exposes an unknown field remains blocked; it cannot be activated by accepting a default. Failure-code additions are additive and versioned; existing codes are never reinterpreted. A logical producer source cannot change during restore or dependency upgrade. If a future semantic source split is unavoidable, a reviewed migration must alias old and new representations to the same semantic identity before dual publication and retain that mapping through every replay and rollback window.

Rollback restores the last accepted exact-version declarative manifest and compatible consumers while preserving PostgreSQL outbox, delivery-attempt, processed-event, terminal-failure, dead-letter, and audit state. It never returns to finite broker `MaxDeliver`, asynchronous persistence, plaintext transport, an old/revoked at-rest key, an open manifest, or a source identity containing deployment/runtime state. TLS rollback is a forward certificate rotation; at-rest rollback keeps the current key and recovers forward rather than reactivating a retired predecessor. If the old binary cannot read the current closed state or retained data, stop publication/consumption and recover forward. It never deletes an acknowledged authoritative mutation. A superseding decision must include account/subject/source migration, cross-domain non-transfer proof, terminal-state compatibility, encryption-key/replay/backup compatibility, performance evidence, and project-owner approval if it changes a locked subject, broker, or security-domain decision.
