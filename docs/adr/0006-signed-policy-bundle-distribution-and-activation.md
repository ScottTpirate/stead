## Context and decision scope

Stead policy decisions must be deterministic, versioned, signed, tested, portable, auditable, and usable without an unapproved network dependency. Security-label profiles are signed policy bundles. Stock OpenFGA models must have model and migration tests. A request must never combine a relationship result from one authorization model with classification rules from another activation generation.

`ADR-CAND-007` leaves the bundle artifact, signing profile, trust-root rotation, connected and air-gap distribution, verification, activation, rollback, and coordination with OpenFGA model migration unresolved. This ADR selects those mechanisms. ADR-0005 separately selects the native in-process Go evaluator, zero decision cache, and the two closed deployment-selected disclosure/revocation modes. `ADR-CAND-002` still selects physical PostgreSQL namespace and migration coordination before any activation/outbox table is implemented; this ADR defines the logical atomicity and ownership contract without preempting that storage decision. This ADR consumes the deployment security-domain's profile-qualified ceilings, `disclosure_revocation_mode`, trust/signing threshold, custody/separation rules, and approved cryptographic boundary as signed/validated inputs; it does not infer any of them from a label-profile ID. It does not change the implementation-neutral policy input/output schemas, rule meanings, OpenFGA responsibilities, security-label algebra, or release-signing requirements for other artifacts.

The Phase 0 security-label profile schema used `bundle_signing.format: sigstore-bundle` as a non-materialized gate while this choice remained explicitly deferred. The official [Sigstore Bundle format](https://docs.sigstore.dev/about/bundle/) fixes an in-toto payload type and a single signature for its DSSE form, so it cannot be treated as an alias for the multiple-signature offline profile selected here. Acceptance of this ADR replaces that provisional value with `stead-policy-activation-set-dsse-v1` before any production policy consumer exists. Images, charts, and other release artifacts retain their separate Sigstore/Cosign-compatible signing requirement.

## Decision drivers

- Verification from local bytes and pinned trust roots with the network physically unavailable
- One content-addressed unit that binds policy rules, profiles, schemas, evidence, and the exact OpenFGA model source
- No mixed model/bundle decisions during concurrent or HA rollout
- Fail-closed handling of tampering, unsupported versions, trust loss, partial distribution, and migration failure
- Planned and emergency trust-root rotation without a vendor, SaaS, transparency log, or public PKI dependency
- Deterministic builds, small standard-library implementation surface, permissive licensing, and compatibility with deployment-selected validated cryptographic boundaries
- Safe rollback that cannot revive a revoked key, stale allow, lowered label, or incompatible tuple representation
- Complete audit, backup/restore, installation, and release evidence

## Considered options

1. **A Stead Policy Activation Set with a deterministic unsigned payload, DSSE v1.0.0 envelope, SHA-256 content addressing, an ECDSA P-256 signing profile, offline trust store, and atomic activation pointer.** DSSE signs exact payload bytes without trusting archive or transport metadata. P-256/SHA-256 is supported by Go's standard library and can be used through an approved validated cryptographic boundary when the deployment security-domain policy requires it, without claiming that the normal build is validated. Accepted.
2. **Sigstore keyless signing with Fulcio/Rekor/cosign as the mandatory verifier.** Strong ecosystem and transparency properties, but keyless verification introduces identity, transparency-log, tooling, network, and air-gap mirroring dependencies. It may be added as supplementary release evidence after approval, but cannot be the canonical activation trust root. Rejected as mandatory architecture.
3. **OCI registry signature/referrer state as the sole authority.** Useful transport metadata, but a registry is not available in every local or air-gapped deployment, mutable tags are unsafe, and registry reachability must not control policy evaluation. OCI-by-digest remains an optional transport only. Rejected as the trust source.
4. **JWS/CMS with general Web PKI or an installation TLS certificate.** These formats can sign bytes, but general certificate-path policy and TLS-key reuse add unnecessary CA, EKU, revocation, and operational ambiguity. Rejected.
5. **Repository commit signatures, transport TLS, checksums alone, unsigned local files, or automatic “last known good” fallback.** None independently proves that an authorized policy signer approved the exact activation contents; fallback may restore a revoked or vulnerable policy. Rejected as nonconforming.
6. **[The Update Framework (TUF)](https://theupdateframework.github.io/specification/latest/) for trust-root and update/distribution metadata.** TUF's root, targets, snapshot, and timestamp roles, threshold signatures, root rotation, version checks, expirations, and consistent snapshots can protect a connected or offline repository against rollback, freeze, and mix-and-match attacks. Those mechanisms are useful supplementary distribution protection, but they do not atomically bind the locally uploaded OpenFGA model ID/read-back digest, tuple migration, native evaluator ABI, Policy Activation Set, replica readiness, PostgreSQL pointer/outbox, and installation anti-rollback anchor. Making TUF mandatory in v1 would add repository-metadata roles, expiry/refresh operations, client code/dependency review, and air-gap metadata handling without replacing Stead's runtime activation protocol. **REJECTED-FOR-V1** as the canonical activation authority or required dependency. A later dependency-approved ADR MAY add TUF as a supplementary transport/update layer whose targets bind the exact activation archive and release-attestation digests; TUF metadata may never authorize activation, substitute for either DSSE envelope, relax the deployment trust threshold, or create automatic rollback/fallback.

No configured switch selects among these trust architectures. Supplementary signatures may be carried for release provenance, but the canonical acceptance rule below must still pass.

## Decision

### Policy Activation Set v1

The deployable unit is a **Stead Policy Activation Set v1**. It binds all policy material needed for one coherent authorization generation:

- the policy input and output schema IDs and SHA-256 digests;
- the canonical decision-table and rule-data digests;
- every included security-label profile ID, version, digest, closed semantic-rule tables, scope/provenance metadata, authoritative snapshot payload/digest, registry-mapping/test-evidence binding, and presentation-renderer contract;
- included deployment security-domain policy ID, version, digest, the profile-ID-keyed ceiling map, the closed `disclosure_revocation_mode`, the v0.1 empty bridge set, trust/signing and recovery threshold, custody/separation requirement, approved cryptographic boundary/evidence requirement, and the evaluated assurance result;
- evaluator ABI/contract version and supported Stead versions;
- the exact OpenFGA 1.1 model source path, SHA-256 digest, compatibility identifier, and tuple-migration identifier;
- required context, reason-code, obligation, and explicit-deny registries;
- every payload file's normalized relative path, media type, byte length, and SHA-256 digest;
- build source revision, dependency-lock digest, build recipe/version, and evidence-manifest digest;
- issue and expiry times, target `trust_set_id` and trust epoch, compatible predecessor activation-set IDs, and rollback constraints.

The signed manifest does not contain secrets, private keys, tenant data, authorization tuples, protected resource identifiers, or deployment credentials.

`policy_bundle_id` is `sha256:<lowercase-hex>` over the exact bytes of the policy content index named by the manifest. `activation_set_id` is `sha256:<lowercase-hex>` over the exact DSSE payload bytes. `signed_envelope_digest` is SHA-256 over the exact released `manifest.dsse.json` bytes, and `archive_digest` is SHA-256 over the exact released tar bytes. The latter two distinguish separate valid signing ceremonies over one activation-set payload and bind the accepted activation envelope and transport artifact. `release_attestation_id` is `sha256:<lowercase-hex>` over the exact post-signing release-attestation DSSE payload bytes, and `release_attestation_envelope_digest` is SHA-256 over that attestation's exact released DSSE envelope bytes. The OpenFGA runtime model ID is installation-local and is not known at build time; staging retrieves the uploaded model by its returned ID, verifies that its canonical source digest equals the signed manifest digest, and stores that verified binding in the local activation record.

### Deterministic unsigned content and strict package profile

For one fixed signed envelope, the portable file form is an uncompressed, deterministically laid-out POSIX tar archive containing:

```text
manifest.dsse.json
payload/...
evidence/...
```

Entries are sorted lexicographically; owner/group IDs and names are empty/zero; timestamps are zero; modes are fixed to read-only regular-file or directory values. The archive uses only bounded POSIX ustar directory and regular-file entries; PAX/global-PAX headers, GNU long-name/long-link headers, and every other tar extension are rejected rather than interpreted. Absolute paths, `..`, backslashes, duplicate normalized paths, sparse files, device nodes, FIFOs, sockets, symlinks, hardlinks, setuid/setgid bits, and undeclared files are forbidden. `manifest.dsse.json` is the sole outer-envelope exception to manifest file listing because it cannot digest-list itself. Every regular file below `payload/` and `evidence/` must appear exactly once in the signed manifest with normalized path, type, length, and digest, and no other regular file is accepted. Files below `evidence/` are pre-signing build, SBOM, provenance, test, mutation, vulnerability, license, and review inputs only; they cannot name the not-yet-created activation-set ID, activation-envelope digest, archive digest, release-attestation ID, or release-attestation-envelope digest. The exact activation envelope and complete archive are instead bound after construction by the companion release attestation and then by the local activation record.

The v1 writer and verifier enforce these ceilings before allocation or staging: 64 MiB exact tar bytes; 512 total entries of which at most 256 are regular files; 8 MiB per regular file; 48 MiB total regular-file content; normalized UTF-8 path length 240 bytes; at most 16 path components and 100 UTF-8 bytes per component. Size and count arithmetic is overflow-safe, and declared tar sizes cannot cause allocation before the remaining raw/content budgets are checked. Deployments may lower but not raise these v1 ceilings. A larger legitimate set requires a superseding profile version/ADR. The verifier opens files without following links and verifies every size and digest before parsing any policy content. Unknown required media types, duplicate JSON keys, unknown signed-manifest fields, invalid UTF-8, floating-point numbers, or non-normalized paths reject the set.

The manifest payload is UTF-8 JSON with fixed field order emitted by typed code, integer sizes, RFC 3339 UTC timestamps, sorted arrays where order is not semantic, no insignificant whitespace, and no duplicate keys. DSSE signs the exact payload bytes; semantic reserialization is never used for verification. Two isolated unsigned builds from the same source, dependency lock, build recipe, and declared build metadata must produce identical payload bytes, payload-file bytes/digests, `policy_bundle_id`, and `activation_set_id`.

Signing is a separate release ceremony. ECDSA signatures are not assumed to be byte-deterministic, so repeating a valid signing ceremony may produce a different `manifest.dsse.json` and final archive digest while signing the same activation-set payload. One ceremony's accepted signed envelope is packaged once; with that exact envelope fixed, the archive layout is deterministic. Only after both the exact envelope and archive exist does the release workflow construct and sign the companion release attestation described below. The exact released archive and attestation-envelope bytes—not reconstructed or re-signed equivalents—must be identical in the installation directory, OCI-by-digest transport, and air-gap bundle.

### Post-signing release and transport attestation

Every released activation archive has a mandatory external **Stead Policy Release Attestation v1**. Its DSSE payload type is `application/vnd.stead.policy-release-attestation.v1+json`. The canonical payload binds the `activation_set_id`, `signed_envelope_digest`, `archive_digest`, embedded pre-signing evidence-manifest digest, policy/model/trust-set/trust-envelope identities, deployment security-domain policy ID/version/digest, exact `disclosure_revocation_mode`, evaluated assurance result, activation-signing key/custodian IDs and threshold result, source revision, WS-09 builder/release-workflow identity, final reviewer approvals and waiver state, and the result digest of the network-disabled verification performed against that exact archive. Later transport descriptors and air-gap indexes may bind the completed archive/attestation pair, but neither digest enters the already signed release-attestation payload.

The release-attestation payload does not contain its own `release_attestation_id` or `release_attestation_envelope_digest`; those identities are computed only after the payload and envelope exist. The attestation is signed under the same active release-policy key purpose and deployment trust-policy threshold as the activation set, using the signature/parser rules below. It remains outside the activation archive: neither `activation_set_id` nor `archive_digest` includes release-attestation bytes, while the attestation payload deliberately includes both of those already-finalized values. Only the release attestation's own ID/envelope digest and any later transport descriptor or media-index self-digest are excluded from its payload. The pair is constructible in one direction: deterministic payload and pre-signing evidence → activation-set signature → archive → release-attestation payload/signature. Verification proceeds in the same dependency order and rejects a valid archive paired with an attestation for any other envelope, archive, trust set, evidence manifest, source revision, or release ceremony.

The activation archive's signature authorizes its exact policy/model content; the release attestation authorizes the exact signed envelope/archive ceremony and its post-signing release evidence. Neither can substitute for the other. One archive may have more than one cryptographically valid release attestation only through a distinct approved ceremony, but activation selects one exact `release_attestation_id` and envelope digest and every replica, credential, audit, backup, rollback, and transport record binds that selected pair.

### Signature and key profile

`manifest.dsse.json`, every policy trust-set envelope, and the external release-attestation envelope follow the [DSSE v1.0.0 protocol](https://github.com/secure-systems-lab/dsse/blob/v1.0.0/protocol.md) and [envelope rules](https://github.com/secure-systems-lab/dsse/blob/v1.0.0/envelope.md) with:

- payload type `application/vnd.stead.policy-activation-manifest.v1+json` for the activation manifest, `application/vnd.stead.policy-trust-set.v1+json` for a trust set, or `application/vnd.stead.policy-release-attestation.v1+json` for the external release attestation, with no cross-type acceptance;
- the exact selected activation-manifest, trust-set, or release-attestation payload bytes encoded by DSSE;
- one or more signatures identified by `keyid`;
- DSSE pre-authentication encoding exactly as specified by DSSE v1.0.0;
- SHA-256 with ECDSA P-256;
- a minimally encoded ASN.1 DER ECDSA signature with low-S normalization;
- public keys encoded as DER SubjectPublicKeyInfo;
- `keyid = sha256:<lowercase-hex-of-SPKI-DER>`.

The Stead writer emits standard RFC 4648 Base64 with canonical padding. The verifier accepts both the standard and URL-safe RFC 4648 alphabets required by DSSE v1.0.0, but this Stead profile intentionally requires correct canonical padding and rejects absent/excess padding or a mixed alphabet; decoded bytes, not the textual encoding, enter PAE and signature verification. Unknown **envelope** fields are ignored as required by DSSE, while unknown fields inside any signed Stead activation-manifest, trust-set, or release-attestation payload remain a contract error. Duplicate JSON keys reject.

Before JSON parsing, Base64 decoding, signature selection, or archive extraction, every activation-manifest, trust-set, and release-attestation DSSE envelope is subject to fixed v1 ceilings: 4 MiB total envelope bytes, 2 MiB decoded payload bytes, JSON nesting depth 32, at most 16 signature entries, at most 256 encoded or 128 decoded bytes per signature, and at most 80 UTF-8 bytes per `keyid`. The verifier checks encoded/decoded lengths with overflow-safe arithmetic before allocation and never allocates from an untrusted declared length. Unknown envelope fields remain ignorable only within the total envelope/depth ceilings; they cannot bypass them. Deployments may configure lower limits but not raise these v1 ceilings. A larger valid future artifact requires a superseding profile version/ADR rather than an unbounded parser path.

`keyid` is an unauthenticated key-selection hint, never proof of signer identity or authority. The verifier selects only keys from the exact active/proposed trust set, recomputes each key's SPKI digest, and counts a signature only after cryptographic verification under that key and purpose. Every trusted key entry binds a stable signed `custodian_id`, purpose, status, and validity interval. A threshold counts distinct verified SPKI keys—and, when required by the deployment trust policy, distinct signed custodian IDs—not signature entries. Two keys controlled by one custodian cannot satisfy custodian separation. Missing/unknown custodians, aliases for the same SPKI/custodian, duplicate key IDs, or multiple valid signatures by one key count once and are rejected when presented to satisfy a threshold.

Verification rejects an unknown algorithm, curve, payload type, unknown or mismatched key-selection hint, malformed/non-minimal DER value, high-S signature, key/signature mismatch, expired/not-yet-valid signer, revoked key, insufficient distinct-key threshold, or activation set whose declared trust-set identity and epoch differ from the candidate activation tuple. It verifies signatures in constant-shape code where the standard library permits and never logs payloads, public-key bodies, or signature bytes as normal telemetry.

Low-S and strict DER prevent alternate encodings of one ECDSA result; they do not make the signing operation deterministic. Reproducibility is asserted for the unsigned content identity and for distribution of one already signed release artifact, not across repeated ECDSA ceremonies.

Release signing keys are offline or held by an approved signing service/HSM boundary. Application replicas, workers, providers, and bundles never receive signing private keys. Verification keys are public but integrity-protected by the installation trust store. The normal Go build does not claim FIPS validation. The deployment security-domain trust policy selects the required signing threshold, distinct-custodian/separation rules, and approved cryptographic boundary under `ADR-CAND-015` where applicable; a label-profile name never changes cryptographic behavior. This signature format is compatible with that later selection.

### Trust store, threshold, and rotation

Each installation has a versioned offline-verifiable trust store containing a monotonically increasing trust epoch, previous trust-set ID, accepted key IDs and SPKI values, stable custodian IDs, purpose, status, validity interval, signature threshold, and a separately identified recovery key. It binds the active deployment security-domain policy ID, version, digest, and evaluated assurance requirements. `trust_set_id` is `sha256:<lowercase-hex>` over the exact trust-set DSSE payload bytes; `trust_set_envelope_digest` is SHA-256 over its accepted signed envelope. Epoch is only ordering metadata and never substitutes for either immutable identity. Bootstrap trust is installed from the verified release or air-gap media and its fingerprint is shown for operator verification. A key embedded only in a candidate activation set or trust update is never trusted by that fact.

Each activation set, trust-set update, and release attestation must satisfy the exact threshold, key purpose, custodian distinctness, and separation requirements in the active deployment security-domain trust policy. The checked-in standard starter domain uses one active release-policy key; the high-assurance starter example uses multiple distinct custodians. These are data-driven examples, not code branches or universal claims. An activation-envelope signature does not count toward the companion attestation threshold or vice versa. Local development still uses a generated instance-local development key and visibly non-production trust store; it never disables signature verification and its key is rejected by production deployment policies.

Planned rotation uses quarantined verification and one atomic transition; trust never changes in an interval before its companion activation set:

1. Build a higher-epoch trust-set update of type `application/vnd.stead.policy-trust-set.v1+json` that names the current `trust_set_id` as predecessor. The current threshold signs the update, and every incoming key separately signs it to prove possession. Stage it as untrusted candidate bytes; it has no authority yet.
2. Stage a companion activation set and release attestation that declare and bind the candidate `trust_set_id` and epoch. Verify the trust update under the current trust set, then verify the companion activation set and its post-signing attestation under the candidate trust set in a quarantined verifier that cannot authorize requests. Preload the exact trust envelope, activation envelope/archive, and release-attestation envelope and obtain replica acknowledgments for all identities and digests.
3. Atomically compare-and-swap the complete trust-set/model/bundle/evaluator pointer plus its immutable audit/outbox intent. Requests observe either the complete prior tuple or the complete candidate tuple, never candidate trust with prior policy or prior trust with candidate policy.
4. After at least one overlapping tuple has operated with the incoming key, retirement repeats the same protocol: a later trust set signed under the current threshold and retained incoming keys is paired with a companion activation set signed only by keys that remain acceptable after the transition.

Epochs never decrease, and removed or revoked key IDs cannot be reintroduced without an explicit new recovery ceremony and audit reason. The separately stored recovery public key is not an ordinary bundle signer. Emergency rotation requires a recovery-signed, higher-epoch trust set, possession proof from incoming release keys, a companion activation set valid under that proposed trust set, and the approval count, acting-principal types, and separation/custody evidence required by the deployment trust policy. The pair is verified in quarantine and switched atomically. If the recovery key, incoming signer, companion set, monotonic anchor, or required approval is unavailable, there is no unsigned, environment-variable, database, command-line, administrator, or local-mode bypass: protected operations remain denied.

Revocation is forward-only. A key-compromise action either atomically activates a replacement trust/activation pair or commits an `emergency_trust_block` plus immutable audit/outbox intent before acknowledging the revocation; the block immediately makes protected replicas unready until a higher-epoch valid pair is activated. No operation changes trust-set identity, key status, threshold, recovery state, or the emergency block without a PostgreSQL compare-and-swap transaction that commits the authoritative mutation and WS-07-owned audit/event intent through the WS-02-owned `core_outbox` port. If current trust policy no longer accepts the active set's signatures, replicas deny; they do not silently select an older set.

### Continuous validity, trusted time, and anti-rollback state

Activation-set expiry, trust-set validity, signer validity, revocation, and explicit emergency blocks are continuously enforced, not checked only at staging. At the earliest controlling expiry, every protected replica becomes unready and denies without automatic fallback; issued permits and credentials expire no later. Operators receive advance warnings but must activate a renewed compatible pair before expiry.

Offline evaluation uses the trusted policy time supplied by the deployment security domain plus a persisted high-water mark. Each decision atomically compare-and-maxes the normalized trusted time into the protected policy-time substate and receives the accepted high-water value/revision used as `policy_context.now`. For an ordinary composed `request_boundary` read, this comparison and final revision validation are folded into the one logical synchronous authorization/audit operation selected by ADR-0005; this ADR does not require a separate per-decision database transaction. It rejects a wall-clock value earlier than the prior accepted high-water mark beyond the deployment policy's bounded skew, and time rollback never extends an expiry. Concurrent lower/equal updates are no-ops; a higher update is monotonic and never invalidates an otherwise identical activation pointer merely because another request observed a later safe time. Request boundaries, strict bounded-read guards, permit consumption, credential use, streaming disclosure, and continuous-validity checks compare their temporal bound against the latest accepted high-water and deny, revoke, or suppress as their selected mode/effect contract requires after expiry. No network time service is required. Correcting an out-of-range clock requires the same authenticated, audited maintenance path as recovery and may only advance the high-water mark.

Every supported installation also maintains a `TrustMonotonicAnchor` outside the ordinary PostgreSQL/application backup restore set. It has two explicitly distinct monotonic parts:

- an activation/trust anchor binding installation ID, trust-set ID/envelope digest, trust epoch, revoked-key-set digest, activation-set/envelope/archive and release-attestation IDs/digests, activation epoch, and an increasing `activation_sequence`; and
- a policy-time substate containing `policy_time_high_water` and increasing `policy_time_revision`, updated atomically by compare-and-max without changing `activation_sequence` or the PostgreSQL activation pointer.

Only trust-set activation, activation-set selection, forward-audited rollback, or a higher-epoch recovery-pair transition advances `activation_sequence`. Routine request-time advancement and clock-only recovery advance only the policy-time substate. An activation-sequence anchor ahead of PostgreSQL creates the fail-closed forward-completion condition below; a policy-time revision ahead of PostgreSQL's non-authoritative observed copy is normal and does not make the activation pointer stale. Supported implementations may use protected host state, TPM/HSM monotonic storage, or operator-held offline recovery media, but may not require a cloud service. A restore must compare the backup with a current independently retained authoritative anchor and may not select an older trust/activation epoch, `activation_sequence`, revocation set, `policy_time_high_water`, or `policy_time_revision`. Recovery onto a new host may create a new host-local anchor only after an operator-held or other separately protected current anchor record is authenticated and the recovery pair advances its epoch and `activation_sequence`; the authenticated time substate is retained or advanced, never reset. If no current authoritative anchor/revocation/time record can be proven, protected service remains denied; the recovery key, application backup, database state, or human approval cannot by itself establish what “higher” means. Restoring an old backup alone can never resurrect a retired/revoked key, lower trust state, or extend an expiry.

### Distribution and offline verification

The exact same activation-set archive and companion release-attestation envelope bytes support three transports:

- a release/installation directory addressed by archive and release-attestation-envelope SHA-256;
- an OCI artifact set fetched by immutable descriptors/digests from an approved registry;
- inclusion of both exact files in a deployment-policy-approved air-gap bundle with their digests, signatures, trust material, SBOM, provenance, notices, and known-issue manifest.

Transport is not trust. Mutable tags, filenames, registry metadata, TUF-like metadata, HTTPS, repository membership, or filesystem ownership never replace DSSE and content verification. Connected installations may download only from configured allowlisted endpoints using authenticated TLS and an expected digest. Download never activates. TUF is neither a v1 dependency nor an activation authority. Air-gap and normal runtime verification perform no DNS, HTTP, transparency-log, timestamp-authority, public-CA revocation, SaaS, or vendor-license call.

`steadctl policy verify` submits an archive plus its release-attestation envelope to the Stead policy-maintenance API for validation in a temporary restricted staging area. `steadctl policy stage` additionally checks platform/evaluator/schema compatibility, exact trust identity/epoch, continuous-validity bounds, every archive file digest, the signed embedded pre-signing license/dependency/CI evidence, the separately signed post-signing attestation and all of its archive/envelope/evidence bindings, deployable conformance fixtures, OpenFGA model tests, migration plan, monotonic anchor, and rollback target. CI/release performs mutation analysis, full property coverage, and source-level security suites before activation signing; installation verifies that immutable evidence through the activation manifest, verifies the companion release attestation, and reruns the packaged deterministic decision, property, Agent, non-disclosure, provider-bypass, archive, and model conformance fixtures that the installed binary can execute. Runtime staging does not pretend to rerun source mutation analysis. Neither CLI command has direct database/OpenFGA writes or changes the active pointer unless the explicit server-side activation operation completes.

All regular Platform APIs may be unready when trust is expired, revoked, corrupt, or emergency-blocked, so `stead-api` exposes a separate local policy-maintenance listener from the same WS-06 implementation. It is disabled from public ingress, binds an operator-controlled Unix socket (or explicitly configured mutually authenticated loopback endpoint), accepts only verify/stage/doctor and recovery/activation operations, and exposes no protected resource read, arbitrary SQL, tuple write, policy-rule edit, or unsigned activation. `steadctl` is only its typed client. Normal administration requires the current explicit administrative relationship plus policy allow. When current policy cannot be evaluated, recovery mode accepts only a higher-epoch recovery-signed trust/activation pair, incoming-key possession proofs, the configured human approvals, current monotonic anchor, and safe clock advance; it cannot lower an epoch, remove a revocation, alter resource authorization, or disclose product data. Every authoritative change still executes through the server-owned compare-and-swap/audit/outbox ports. This keeps recovery reachable without turning the CLI, host root, or maintenance listener into an authorization bypass.

### Atomic OpenFGA model and policy activation

The authoritative PostgreSQL activation record contains one monotonically increasing activation epoch and exactly one complete tuple:

```text
(activation_set_id, signed_envelope_digest, archive_digest,
 release_attestation_id, release_attestation_envelope_digest,
 policy_bundle_id, openfga_model_id, openfga_model_source_digest,
 deployment_security_domain_policy_id, deployment_policy_version,
 deployment_policy_digest, disclosure_revocation_mode,
 evaluated_assurance_result_digest,
 evaluator_contract_version, trust_set_id, trust_set_envelope_digest,
 trust_epoch, activation_sequence, activation_epoch,
 activated_at, activated_by)
```

Activation uses these phases:

1. Verify and extract the exact activation archive, verify the companion release-attestation envelope and any candidate trust-set envelope without network trust, and bind every payload, activation-envelope, archive, release-attestation, trust-envelope, deployment-policy, disclosure mode, and evaluated-assurance identity/digest. A transition must satisfy the current active trust/deployment policy before candidate authority exists and the candidate policy after activation; a candidate cannot self-authorize a lower threshold, weaker custodian/recovery separation, unapproved cryptographic boundary, unsupported disclosure mode, or other assurance weakening. Missing/unknown mode denies, and changing a profile ID alone cannot change it.
2. Verify the signed immutable pre-signing CI evidence inside the activation archive, including required source mutation/property/security results, and verify the post-signing release attestation's final envelope/archive/evidence/approval bindings; then run the installed binary's packaged schema, decision-table, label-property, Agent-intersection, non-disclosure, provider-bypass, archive, OpenFGA-model, and deterministic-replay conformance fixtures.
3. Upload the exact staged model to stock OpenFGA as a new immutable authorization model. Read it back, normalize it using the versioned model canonicalizer, and compare its digest with the signed source digest.
4. Apply only the signed expand-compatible tuple migration. During coexistence, writes satisfy both current and staged model restrictions; migration verification proves counts, types, delegation/task links, and revocation fences.
5. Preload and compile the exact policy data and proposed trust-set bytes in every serving `stead-api` replica. Each acknowledgment binds replica/build/evaluator versions plus activation-set, policy-bundle, model-source, trust-set, activation-envelope, trust-envelope, archive, release-attestation, release-attestation-envelope, deployment-policy, and disclosure-mode identities/digests; it conveys no policy contents or keys. A candidate `commit_boundary` activation also requires every replica and controlled egress participant to acknowledge the complete ADR-0005 strict capability set; until that later implementation exists, such activation denies rather than falling back.
6. Run shadow conformance against synthetic fixtures only. Shadow mode can compare decisions but cannot authorize, issue credentials, access protected resources, or emit user-visible results.
7. Persist a non-authoritative pending-activation record and intent, then advance the external `TrustMonotonicAnchor` activation/trust part to the proposed `activation_sequence` and complete tuple. This operation is compare-and-advance only and leaves the policy-time substate equal or higher. If it fails, the old pointer remains authoritative. If it succeeds but the process fails before pointer commit, the activation-sequence-ahead condition makes protected services unready; only idempotent forward completion of that exact staged tuple or a higher-epoch recovery ceremony may proceed.
8. In one PostgreSQL transaction, compare the current pointer and advanced anchor, re-prove the active-policy-before/candidate-policy-after assurance and mode-readiness result, then atomically switch the complete trust-set/model/bundle/evaluator/deployment-policy/mode tuple and invoke the WS-02-owned transaction-scoped outbox port to append the immutable WS-07-owned activation/trust/audit event intent. Trust-set activation, key add/retire/revoke, emergency-block clearing, recovery, and policy/model/deployment-policy/mode activation therefore share one authoritative mutation and audit-before-effect commit. The WS-07 publisher and audit consumer materialize that intent idempotently through their owned ports; no component writes another owner's tables directly.
9. Every new request acquires the complete pointer once, verifies replica readiness for every bound identity/digest, selected disclosure mode, and continuous-validity bound, and uses its exact model, bundle, trust set, activation envelope/archive, and release attestation. ADR-0005's final logical authorization/audit operation fences the complete tuple before the applicable request boundary, strict guard, protected effect, or provider credential.

There is no cross-store transaction with OpenFGA or the external monotonic anchor. Atomic authorization state is achieved by creating and verifying immutable candidates first, fail-closing on an activation-sequence-ahead interruption, then switching one authoritative PostgreSQL pointer that binds the trust set, activation envelope/archive, release attestation, returned OpenFGA ID/source digest, evaluator, and bundle. Routine compare-and-max policy-time updates are not activation transitions and do not participate in that pointer transaction; replicas must use the authoritative latest high-water for temporal validity but do not require equality with PostgreSQL's last-observed time copy. Old trust sets, models, bundles, archives, and attestations remain inert and addressable only for compatible forward-audited rollback. A replica that lacks any selected bytes, exact digest/identity, model binding, trust state, valid time, or evaluator ABI fails readiness and denies; it never uses whichever local files happen to exist.

Partial distribution, missing replica acknowledgment, failed OpenFGA read-back, tuple migration mismatch, signature/evidence/conformance failure, activation/trust-anchor failure, PostgreSQL/outbox transaction failure, or stale compare-and-swap cannot select the candidate pointer. An activation-sequence-ahead interruption denies rather than serving the now-older tuple. NATS availability is not checked synchronously and is not part of the activation transaction: the pointer, authoritative trust mutation, audit intent, and outbox row commit together while NATS is unavailable. The worker publishes that outbox row after recovery. PostgreSQL plus the anti-rollback anchor define activation truth, while any lagging event-driven projection suppresses protected results until it reaches the committed activation fence.

### Compatibility and model migration

Every activation set declares the exact Stead/evaluator contract range, policy schema majors, label profiles and their snapshot/evidence inputs, profile-qualified deployment-domain ceiling map, closed disclosure mode and readiness requirements, assurance policy, v0.1 empty bridge set, OpenFGA schema/model digest, tuple migration, and compatible predecessor activation-set IDs. Compatibility is an allowlist, not a best-effort parse. Unknown fields, rules, relations, types, obligations, profile IDs/versions, ceiling bindings, disclosure modes, non-empty bridges, renderer directives, or schema majors fail staging.

OpenFGA changes use expand/migrate/contract. New tuple types or relations are introduced without invalidating current reads; writers produce the compatible form; existing tuples are migrated and verified; both model suites pass; only then may the pointer select the new model. Contract/removal waits until the supported rollback window no longer needs the old representation. Agent, service-account, delegation, task-scope, and independent-revocation tuples receive explicit migration assertions and may not be inferred from requester or Team hierarchy data.

Policy input/output major coexistence follows the platform compatibility policy. One activation set may list multiple supported readers during transition, but one decision names one exact contract and bundle revision. No adapter may translate an unknown rule into allow.

## Consequences

### Security, authorization, classification, and bypass paths

Tampered, partial, unsigned, expired, unknown, untrusted, revoked, incompatible, or untested sets cannot become active. A policy or model directory mounted by an administrator, injected by a provider, received through NATS, or copied into a replica has no authority without successful staging and pointer activation. Database writes cannot select an arbitrary model ID because activation compares the OpenFGA read-back digest and signed binding.

Agent authority is protected by the same signed model/bundle pair. An activation that drops Agent-specific authority, delegation/task scope, runtime/session/resource intersection, or independent revocation fails required tests. Team hierarchy cannot gain an allow edge by migration. Label/profile changes preserve join/no-lowering and invalidate derived projections; cross-domain/write-down stays denied.

The trust store and activation APIs are authorization-controlled administrative resources. Managing policy metadata does not grant protected content access. Lowering/declassification bundles still require the separate reason, source authority, audit, and two-person workflow where configured; signing a bundle is not a downgrade approval.

### Data model, migration, and backward compatibility

This is the first activation mechanism, so no unsigned production bundle is grandfathered. Development fixtures are built into a signed development set before protected functionality is enabled. Persisted activation rows, staged-set inventory, exact disclosure mode, local OpenFGA ID bindings, trust-set IDs/envelope digests/epochs, activation-envelope/archive and release-attestation IDs/digests, `activation_sequence`, last-observed policy-time high-water/revision, replica acknowledgments, migration checkpoints, emergency blocks, and rollback compatibility are owned by WS-06 tables and interfaces. Phase 1 does not persist strict guard/quiescence/buffer state merely to reserve the typed `commit_boundary` seam. Append-only audit records and event schemas remain WS-07-owned; `core_outbox.*` storage and the transaction-scoped insertion port remain WS-02-owned; the WS-07 publisher may claim and mark delivery only through its reviewed repository port. WS-09 owns reproducible builder/signing-workflow integration, embedded pre-signing CI/SBOM/provenance/mutation evidence, and construction of the post-signing release-attestation payload, but it has no runtime activation authority or signing private key by virtue of that ownership.

Bundle, trust-set, activation-envelope, archive, release-attestation, and release-attestation-envelope identities are content identities and never reused. A semantic update produces a new policy bundle and activation set even if a display version is unchanged; a new signing/release ceremony produces new activation-envelope/archive and release-attestation identities even if the activation payload identity is unchanged. Provider, credential, search, event, notification, export, cache, backup, and audit consumers carry the complete activation/trust/release-attestation metadata but do not parse bundle internals.

### Upgrade, rollback, backup, restore, and recovery

Upgrade downloads or receives the exact archive/attestation pair, verifies the signed activation envelope, embedded pre-signing evidence, external release attestation, selected disclosure mode and mode-readiness evidence, stages, migrates, preloads, runs deployable conformance, advances the activation/trust anchor, and only then atomically activates. Pre-anchor abort removes the staged copy without changing active state. An activation-sequence-ahead interruption requires exact forward completion or higher-epoch recovery. A disclosure-mode change is an atomic signed activation, not mutable configuration; `commit_boundary` activation requires the complete strict runtime and separately labeled performance/operations evidence and never silently falls back. Post-activation rollback is a new authorized forward transaction to an explicitly listed compatible predecessor payload under the **current or higher** trust set and a newly signed activation envelope/archive plus release attestation; it repeats current trust, both signatures, continuous expiry/time, binary/schema, OpenFGA read-back, tuple, policy, disclosure-mode readiness, Agent, bypass, anchor, and projection tests.

Rollback never decreases the trust epoch, `activation_sequence`, `policy_time_high_water`, or `policy_time_revision`; never reuses old signing evidence; never reactivates a revoked key; never restores a stale tuple/delegation/revocation revision; never lowers a security label; never undoes an explicit deny; and never selects a bundle incompatible with current data. If the prior policy payload cannot safely interpret current tuples/data or cannot be re-released under current trust, forward recovery is mandatory. There is no automatic health-triggered failback because it could restore a known vulnerable policy; an authorized operator may execute a verified forward-audited rollback while the system remains fail closed.

Backups include active and retained activation-set bytes, exact archive/file/activation-envelope digests, exact release-attestation payload/envelope bytes and digests, signed trust/activation/attestation envelopes, deployment security-domain policy bytes/ID/version/digest, exact disclosure mode, evaluated assurance result, trust store/custodian metadata and recovery-key references, the last observed non-authoritative copy of `activation_sequence`, `policy_time_high_water`, and `policy_time_revision`, local model-ID/source-digest bindings, tuple-migration state, activation/outbox/audit records, applicable strict coordination evidence, and approved rollback payloads. The authoritative current `TrustMonotonicAnchor` is retained separately and is not rolled back by application restore; private signing keys are referenced through their external custody system and are not copied into application backup. Restore verification is offline, compares the backup to that separately retained current anchor, revalidates every activation, release-attestation, trust, deployment-policy/mode/assurance, digest, model, revocation, and time binding, restores only an equal-or-newer authoritative tuple transactionally, and keeps protected services unready until the selected exact archive/attestation/trust/deployment-policy bytes and mode readiness are present on every serving replica. An older backup anchor copy cannot substitute. Higher-epoch recovery still requires authenticated separately retained current anchor/revocation/time evidence; if it is missing, the installation remains denied rather than accepting backup state.

### APIs, schemas, events, providers, and standards mappings

The canonical policy input/output and OpenFGA models remain the public/cross-module contracts. DSSE v1.0.0 is the signature envelope profile; SHA-256 binds activation payload, trust-set, activation envelope, archive, release-attestation payload/envelope, policy, and model content identities; OCI is an optional transport mapping, not a runtime requirement. Activation events use the existing CloudEvents/AsyncAPI/outbox rules and carry safe IDs/digests, actor context, correlation/causation, and outcome without embedding policy files, tuples, keys, or protected resource data.

The first contract implementation changes the security-label profile schema's signing-format constant from the provisional `sigstore-bundle` value to `stead-policy-activation-set-dsse-v1` and updates every checked-in profile in the same commit. Because no production policy consumer or persisted signed bundle exists, this is a pre-compatibility correction rather than a runtime migration. Tests must reject the old value for new v1 materialization; historical Phase 0 source provenance remains in Git and the ADR candidate history rather than as a second accepted format.

No provider may consume raw policy files as its own decision engine. Providers receive only scoped enforcement facts or credentials from the ADR-0005 coordinator. Search, activity, inbox, notifications, and audit views invalidate/rebuild from the committed activation event and current consistency fence; a lagging projection suppresses protected results.

### Observability, audit, privacy, and evidence

Required audit events cover build admission, verify, reject, stage, pre-signing-evidence result, release-attestation verify/reject, deployable-conformance result, model upload/read-back, tuple migration, replica/mode-readiness acknowledgment, activation-anchor advance/mismatch, policy-time rollback/recovery, activate, mode change, abort, rollback, continuous-expiry denial, trust-set stage/activate, key add/retire/revoke, emergency block, recovery ceremony, maintenance access, backup, and restore. Records identify acting/requesting principals, authentication context, action, outcome, activation/policy/model/trust-set IDs and digests, activation/trust envelope and archive digests, release-attestation ID/envelope digest, deployment security-domain policy ID/version/digest, exact disclosure mode, evaluated assurance result, activation/trust epochs, `activation_sequence`, accepted `policy_time_high_water`/`policy_time_revision`, key and safe custodian IDs, source revision, embedded-evidence-manifest digest, compatibility/rollback target, safe reason codes, and correlation/causation. Routine successful compare-and-max operations need not create a standalone event when the one logical decision audit records the accepted value; mode/rollback/correction/failure/recovery are mandatory events. Authority-changing records are durably coupled to their mutation through the outbox transaction. They never contain policy payloads, tuples, private keys, signatures, credentials, protected bodies, or unnecessary trusted-attribute values.

Metrics expose the safe closed disclosure-mode label, active epoch, safe truncated build version, stage/activation counts and duration, signature/digest/evidence/attestation/conformance failures, trust/activation expiry windows, clock rollback, anchor mismatch, emergency block, replica/mode readiness, model-binding mismatch, rollback state, and outbox lag. High-cardinality activation/trust/envelope/attestation/key IDs belong in structured audit/log fields, not metric labels. Health and `steadctl doctor` report whether the exact active activation/trust/envelope/archive/release-attestation/deployment-mode set, continuous validity, monotonic anchor, OpenFGA model binding, mode readiness, and rollback target verify; public health does not reveal policy content or protected tenancy.

Pre-signing evidence inside `evidence/` binds the source revision, WS-09 builder identity, dependency lock, policy/model/trust-set/trust-envelope content known before activation signing, SBOM, provenance, test/property/mutation results, vulnerability/license results, and then-current reviews/waivers. Its files are digest-listed by the signed activation manifest, so they are immutable and independently verifiable offline, but they do not claim any identity that depends on the later activation signature or archive.

The separately signed release attestation binds that embedded-evidence-manifest digest plus the final `activation_set_id`, activation-envelope/archive digests, activation-signing key/threshold result, final approvals/waiver state, and exact-archive network-disabled verification result. The local activation record then binds the computed release-attestation ID and envelope digest without asking the attestation to sign its own identity. This split is normative: no evidence object may contain a digest that recursively depends on that object's own bytes.

### Dependencies, licenses, supply chain, and portability

The canonical verifier can be implemented with the required Go toolchain and standard-library `archive/tar`, `crypto/ecdsa`, `crypto/elliptic`, `crypto/sha256`, `crypto/x509`, `encoding/asn1`, `encoding/base64`, and `encoding/json` packages plus small Apache-2.0 Stead DSSE/profile code. No OPA/Rego, cosign, Fulcio, Rekor, public CA, timestamp service, OCI registry, cloud KMS, HSM, or proprietary signing service is required at runtime.

An implementation may integrate an approved HSM/KMS or supplementary Sigstore evidence through adapters, but the offline verifier and portable artifact remain functional without it. Any third-party DSSE, OCI, canonicalization, cryptographic, or archive library requires exact dependency/license/security approval, SBOM inclusion, pinned provenance, and conformance tests before import. Unknown or disallowed licenses fail release. Private-key custody adapters never become part of policy evaluation.

The signature profile uses an algorithm that can be supplied by a FIPS-validated boundary, but it does not assert that the default Go binary or any installation is FIPS validated. The exact approved module/provider boundary, enabled-mode proof, custody threshold, and evidence remain deployment-policy inputs deferred to `ADR-CAND-015`; the same controls may be required by a high-assurance non-government deployment. TUF is not a selected dependency in this ADR. Any later TUF client or metadata implementation follows the same exact dependency/license/security/air-gap approval workflow and the supplementary-only boundary above.

Operator documentation must cover fingerprints and every content identity, staging, maintenance-listener authentication, verification, trust rotation/recovery, continuous expiry and clock rollback, monotonic anchors, HA acknowledgment, activation, rollback, backup/restore, air-gap media, and fail-closed recovery. Procedures must use copyable identifiers, clear non-color-only status, accessible tables/output, and explicit confirmation of high-impact trust or activation changes without exposing key material.
